# 평가 파이프라인 실행 가이드 및 실행 가능성 점검

점검: 2026-09-02
결론: **원격 세션에서는 실행 불가.** 아래 A의 두 가지 이유 때문이며, 실행은 로컬 Windows 환경에서 직접 해야 한다.

---

## A. 실행 불가 사유

### A-1. OpenAI API 차단

| 환경 | pypi.org | api.openai.com |
|---|---|---|
| 로컬 Linux VM (device_bash) | ✅ 200 | ❌ `Tunnel connection failed: 403 Forbidden` |
| 원격 클라우드 컨테이너 | ✅ 200 | ❌ 동일 |

두 환경 모두 egress 허용 목록에 OpenAI가 없다. `run`, `judge` 등 LLM 호출이 필요한 명령은
**사용자의 Windows 환경에서 `.venv`로 직접 실행**해야 한다.

> 참고: 프로젝트의 `.venv`는 Windows용(`Scripts/`, `Lib/`)이라 Linux VM에서 사용할 수 없고,
> Linux VM의 시스템 python3에는 langchain·langgraph·faiss·openai가 설치되어 있지 않다.
> (pandas, python-dotenv만 존재)

### A-2. 원자료 workbook 부재 — ★ 더 근본적인 문제

`evaluation/dataset.py`의 `prepare_legacy_cases()`는 다음을 요구한다.

```python
all_cases = pd.read_excel(source_xlsx, sheet_name="전체 데이터(80)")
improved   = pd.read_excel(source_xlsx, sheet_name="개선된 사례")
# 필요 컬럼: Input_Message, User, Baseline_Matched_Message, new_matched_message
# 검증: 개선 사례 수가 정확히 39가 아니면 ValueError
```

그러나 프로젝트 폴더의 `0522_data.xlsx`는 **`Sheet1` 하나뿐이고 17,345행 × 3열의 메시지 코퍼스**다.
challenge set 80건이 담긴 workbook은 폴더 어디에도 없다.

`evaluation/README.md`도 이를 전제하고 있다.

> *"원본 workbook을 **별도 보관한 상태에서** `prepare`로 SHA-256 계보를 포함해 재생성한다."*
> Quick start의 `--source-xlsx <legacy-cases.xlsx>`는 플레이스홀더이며 `0522_data.xlsx`가 아니다.

**해당 workbook을 찾아야 파이프라인 전체가 시작된다.**

## B. ⚠️ 원고 §5.2 · §5.3 수치에 근거 로그가 없다

프로젝트 전체를 검색한 결과:

- `evaluation/data/`, `evaluation/runs/`, `evaluation/reports/` — **전부 없음**
- `*.jsonl` — **0건**
- `test_result.xlsx` — 설문 안내문 2행짜리. 실행 로그 아님

즉 다음 두 수치는 현재 **재현 근거가 프로젝트에 없다.**

| 원고 위치 | 수치 | 근거 상태 |
|---|---|---|
| §5.2 | 노드 통과 수 분포(80건), 최빈 8 / 평균 7.96 / 최대 14 | 히스토그램 PNG만 존재. 원자료 없음 |

> 이는 `양방향 매칭 44.1%`를 삭제한 사유("재현 데이터 없음")와 **같은 상황**이다.
> 심사 중 원자료 제출을 요구받으면 대응이 어렵다. 우선순위를 높여 workbook을 확보할 것.

※ §5.4(설문)는 `docs/ratings_ver3.xlsx`의 `rating2` 시트가 원자료로 남아 있어 재현 가능하다.

## C. 로컬에서 실행할 명령 (Windows PowerShell)

`.venv` 활성화 후, 프로젝트 루트에서.

### C-1. 케이스 생성 (LLM 비용 0)

```powershell
python -m evaluation.cli prepare `
  --source-xlsx <challenge-80건이-든-workbook>.xlsx `
  --ratings-xlsx docs\ratings_ver3.xlsx
```

→ `evaluation/data/challenge_80.jsonl`, `human_ratings_40x3.jsonl` 생성

### C-2. 파일럿 3건 — 실제 토큰·시간 실측

```powershell
python -m evaluation.cli run --limit 3 --output evaluation\runs\pilot.jsonl
python -m evaluation.cli run-report --runs evaluation\runs\pilot.jsonl
```

**여기서 나온 비용을 80건으로 환산해 전체 실행 여부를 결정할 것.**

### C-3. 전체 80건

```powershell
python -m evaluation.cli run --output evaluation\runs\full80.jsonl
python -m evaluation.cli run-report --runs evaluation\runs\full80.jsonl
```

중단되어도 같은 명령으로 재개된다(케이스별 append + fingerprint 검증).

### C-4. LLM 심판 (선택)

```powershell
python -m evaluation.cli judge --runs evaluation\runs\full80.jsonl `
  --output evaluation\runs\judge80.jsonl --model gpt-4o-mini
```

> ⚠️ 시스템이 gpt-4o이므로 심판도 gpt-4o 계열이면 **self-preference bias** 지적을 받는다.
> 다른 계열 모델로 교체하거나, 두 모델로 돌려 일치도를 함께 보고할 것.

## E. Query Rewrite 성능 지표 설계

### E-1. 추가 실행이 필요 없다

`matching_agent/nodes.py`의 `retrieve()`는 **원문 메시지도 쿼리로 함께 검색한다.**

```python
queries = [("original", state["input_message"])]
queries.extend((f"reformed_{i}", q) for i, q in enumerate(reformed_queries, 1))
```

그리고 `retriever.collect_candidate_hits()`가 후보마다
`{query, query_kind, rank, score}`를 `sources`에 누적한다.

→ **"쿼리 재구성 없음" 조건이 모든 실행에 내장되어 있다.** 절제 실행을 따로 돌릴 필요가 없고,
로그만으로 아래 지표가 전부 계산된다.

### E-2. 계산 가능한 지표

| 지표 | 정의 | gold 필요 |
|---|---|---|
| **재구성 기여율** ★ | 최종 선택 후보 중 `query_kind == "original"` 출처가 **없는** 비율 | 불필요 |
| 후보군 확장률 | 중복 제거 후 후보 수 ÷ 5 | 불필요 |
| Recall@5 vs Recall@15 | 선택 후보가 원문 Top-5에 포함 vs 전체 후보군에 포함 | 대용 정답 |
| MRR | 선택 후보의 원문 쿼리 내 순위 역수(미포함 시 0) | 대용 정답 |

★가 가장 강력하다. **"재구성이 없었다면 이 후보는 후보군에 존재하지 않았다"**는 사실 기술이므로
순환 논리에 해당하지 않는다.

### E-3. 원고와의 연결

§4.2 (3)의 다음 문장은 현재 **근거 없이 주장**되고 있다.

> *"중복되는 메시지를 제거함으로써 최종적으로 하나의 후보 리스트를 형성한다.
> 이는 후보군의 Recall(검색 대상 중 실제 정답을 찾아내는 비율)을 극대화할 수 있다."*

E-2의 지표가 정확히 이 주장의 근거가 된다.

### E-4. MRR보다 Recall이 적절한 이유

1. MRR은 정답이 1개이고 순위가 결과에 직접 영향을 줄 때 쓰는 지표다
2. 본 시스템은 Top-5 × 3쿼리 → 중복 제거 → **Selector가 재정렬**하므로 검색 순위가 최종 결과를 결정하지 않는다
3. `evaluation/README.md`도 *"gold match/acceptable-set annotation이 아직 없으므로 Recall@k, MRR, nDCG는 계산하지 않는다"*고 명시하고 있다
   → E-2의 ★ 지표는 gold가 필요 없으므로 이 제약을 우회한다

## F. 절제 실험(ablation)을 한다면

`graph.py`에 절제 스위치가 없어 코드 수정이 필요하다. 두 군데뿐이다.

```
① 쿼리 재구성 제거  → Query_Reformer가 원문을 그대로 쿼리로 반환하도록 분기
② Selector 분화 제거 → Retrieve → [TypeMatch, RoleMatch, PersonaMatch] → Selector 를
                        Retrieve → Selector 로 직결
```

`build_matching_graph(ablation=None|"no_reform"|"no_split")` 인자 하나면 된다.

**baseline 조건은 재실행 불필요** — 케이스에 `legacy_baseline_output`이 이미 포함된다.
**절제 조건은 재탐색 루프를 끄는 것이 방법론적으로 옳다**(변수 통제). 노드 수가 4~5로 줄어 비용도 감소한다.

> ⚠️ 절제 결과에서 각 요소의 기여가 미미하게 나오면 논문이 오히려 약해질 수 있다.
> 현재 §6.4는 이를 "규명되어야 할 과제"로 열어두고 있으며, 열어두는 것도 정당한 선택이다.
